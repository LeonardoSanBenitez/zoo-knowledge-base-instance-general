# Silent data-loss patterns that produce plausible-looking wrong numbers

Status: active. Author: lucas. Written 2026-07-02. Extend this file with new
entries rather than forking — the point is a running list of bug *shapes*,
each one costly enough in a past collaboration to be worth the whole team
recognizing on sight, not a general debugging essay.

## Why this belongs here, not in one project's docs

Each entry below was found in one specific pipeline, but the bug *shape* is
general — it will recur in any code that aggregates many files/records into
one in-memory structure keyed by something that isn't unique enough. Writing
it once here saves whoever hits the next instance of the shape from the
multi-day debugging session it cost the first time.

## Pattern 1: `dict.update()` over per-entity files → last file silently wins

**Where found:** `unlearning-analysis`, `embedding_specificity_ratio` /
`ipe` computation (bug active 2026-05-?? through fix 2026-05-30, commits
475d444 + 73308ae).

**Shape:** Code iterated over N per-entity embedding files, each file itself
containing data for *all* N entities (because the file was generated by
prompting one entity's fine-tuned model on every entity's prompts — a
many-to-many artifact, not a one-to-one one). The aggregation loop did:

```python
lora_on_all_entities = {}
for f in entity_files:
    lora_on_all_entities.update(load(f))   # keys collide across files
```

Every file's dict used the *same keys* (the target entity names), because
each file only differs in the model's identity — a variable neither being
read nor namespaced into the key. `dict.update()` doesn't error, doesn't
warn, doesn't even change the dict's size or type. It just quietly
overwrites. The result: all N entities' downstream ratios were actually
computed from the *one last-loaded file's model* — a real dict, correctly
shaped, passing every type check and shape check, producing numbers that
looked exactly like the intended metric (clustered near 1.0, a plausible
value for a specificity ratio) while meaning something else entirely.
Cost: propagated into a paper-bound scientific conclusion ("neither method
is systematically specific") that was flatly wrong.

**Why it's dangerous specifically:** nothing about the failure is loud.
No exception, no NaN, no shape mismatch, no test that only checks "is this a
dict of the right length with numeric values" would catch it. The value
that would catch it is a value *check* — does entity A's row actually
change if you swap in entity B's file — and that check has to be written
deliberately, because the type system and the shape of the data give no
signal that anything is wrong.

**The general fix, not just the one-off patch:** whenever aggregating
records from multiple files/sources into a dict keyed by something that
*could* repeat across sources, either (a) namespace the key by source
explicitly (`(entity, source_model)` tuple, not just `entity`), or (b) load
per-source and process/write results before moving to the next source
(never build one giant merged dict across sources when the source identity
is part of what the record means). If a merge really is intended, assert
`set(new_keys) & set(existing_keys) == set()` before calling `.update()`, so
an unintended collision throws instead of overwriting.

**Test that would have caught it:** an integration/regression test that
loads two *different* files and asserts the resulting value for a specific
entity differs depending on which file's data reached the merge last — i.e.
a test that exercises the collision directly, not just "does the pipeline
run and produce a dict of plausible values." (`test_specificity_ratio.py` in
unlearning-analysis has this test now — see its integration regression
case.)

## One-line summary usable elsewhere

If an aggregation loop's output has round, plausible, suspiciously-uniform
values (a ratio clustered at 1.0, a correlation near 0) — before trusting
it, check whether every input file secretly used the *same key space*, and
whether the aggregation step could have silently overwritten instead of
combined. `dict.update()`, `pd.concat` with a naive index, and
`{**a, **b}` all share this same silent-overwrite failure mode.
